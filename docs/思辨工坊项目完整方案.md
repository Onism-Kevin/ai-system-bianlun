# 思辨工坊：高校师生议题研究与论证训练平台

> 项目完整方案（产品定位、功能设计、技术实现与竞赛准备）  
> 版本：1.0  
> 日期：2026-10-09

## 1. 项目概述

### 1.1 项目名称

**思辨工坊——面向高校师生的议题研究与论证训练平台**

### 1.2 一句话介绍

面向高校学生与教师，围绕课程和现实议题，提供问题拆解、观点构建、人机对练、证据提示、论证图谱和训练复盘，帮助用户练习形成、检验和修订观点。

### 1.3 项目定位

本项目基于现有 AI 辩论系统改造。原有 AI 正反方辩论、人机辩论、裁判总结和辩论存档继续保留，但从产品主体转为学习训练能力。项目的核心目标从“生成一场辩论”转为“帮助师生研究议题、建立论证并复盘思维过程”。

学生和教师都是系统的服务对象与训练对象：

- 学生通过议题探索、论证练习、质疑回应和观点修订提升课程研究与表达能力。
- 教师通过议题分析、课堂提问设计、教学情境演练和教学复盘提升思辨与教学引导能力。
- 教师也可以创建课程训练任务，组织学生使用系统并查看有权限的学习成果。

### 1.4 首版目标用户

- 高校学生：课程讨论、小组汇报、课程论文和现实议题研究的准备者。
- 高校教师：通识课程、写作课程、思政与专业课程中需要组织议题讨论和论证训练的教师。

辩论社成员可作为早期高频试用用户，但项目不只面向辩论社。特殊教育辅助表达方向作为未来经专业用户研究验证后的拓展，不纳入首版核心范围。

## 2. 现实问题与产品目标

### 2.1 目标问题

师生在课程研究、讨论和表达中可能遇到：

1. 面对复杂议题时直接站队，未能厘清关键概念和讨论边界。
2. 能提出观点，却难说明理由、证据与结论之间的关系。
3. 信息来源多，难以区分事实、观点、推测和仍需核实的说法。
4. 讨论容易变成立场碰撞，缺少有效追问、反例分析和观点修订。
5. 收到的反馈比较笼统，练习者不清楚具体从哪里改起。
6. 教师设计思辨活动、跟进学生练习和整理课堂复盘材料需要额外时间。

### 2.2 产品目标

将议题学习组织为连续的训练闭环：

> **理解议题 → 构建观点 → 接受质疑 → 检查论证与证据 → 修订观点 → 复盘**

系统提供结构化支架和可检查的反馈，不替师生作最终判断，不将未经核验的模型输出当作事实。

## 3. 产品设计原则

1. **学习者主动**：AI 引导用户思考，不直接代写完整答案。
2. **反馈有依据**：分析尽量指向用户原文、课程材料或可查看的来源。
3. **不确定性可见**：无来源或证据不足时标记“待核实”“AI 推断”或“需要人工判断”。
4. **过程可复盘**：保存观点版本、训练步骤和用户修改，不只保留最终分数。
5. **师生双向服务**：教师既能组织教学，也能进行个人议题思辨和教学情境训练。
6. **功能可验证**：所有效果主张以试用、测试或对照数据为依据。
7. **核心流程优先**：不让文生图、装饰功能或复杂 Agent 架构阻塞训练主流程。

## 4. 功能范围

### 4.1 学生端

#### A. 议题探索

用户输入课程或现实议题，系统协助整理：

- 关键概念和可能定义；
- 议题讨论范围和边界；
- 核心子问题；
- 相关利益主体和分析视角；
- 需要进一步查证的问题。

用户可以编辑、删除、补充系统生成内容。

#### B. 观点建构

提供结构化编辑区，引导用户填写：

- 核心主张；
- 支持理由；
- 证据或材料；
- 可能反例和限制条件；
- 尚未确定的问题。

#### C. 人机论证训练

学生与 AI 进行多轮练习。AI 根据学生当前论证提出针对性追问、反例或证据要求。训练模式包括：

- 教练式追问：逐步提示学生补足论证；
- 反方对练：AI 针对学生观点提出挑战；
- 自由辩论：保留原系统的人机辩论体验。

#### D. 论证结构分析

系统将内容整理为：

- 主张；
- 理由；
- 证据；
- 反例；
- 结论；
- 支持、反驳、补充、依赖或限制等关系；
- 仍未回应的问题；
- 需要核实的事实性陈述。

分析应提供原文片段或材料位置作为依据。缺乏依据的内容需明确标记为 AI 推断或待确认。

#### E. 观点修订与复盘

- 保存初稿、修改稿和最终稿；
- 展示版本差异；
- 生成按统一量表组织的反馈；
- 允许用户填写反思；
- 将练习保存在个人训练档案中。

AI 分数不得单独代表用户能力。报告须展示量表、依据和建议。

### 4.2 教师端

#### A. 教师个人思辨训练

教师可以使用议题拆解、多视角分析、反方质疑、证据提示和论证复盘，用于个人备课、研究或专业议题探索。

#### B. 教学情境演练

教师设定议题、教学目标和情境，由 AI 模拟不同观点的学生或讨论参与者，练习：

- 针对论据不足的观点提出追问；
- 帮助讨论回到证据和论证；
- 引入其他视角；
- 总结分歧并提出后续讨论方向。

系统提供练习反馈，但不自动评定教师真实教学能力。

#### C. 课程任务设计

教师可以：

- 创建、编辑、关闭议题任务；
- 设置训练目标、步骤、提交格式和评价维度；
- 上传或关联课程材料；
- 生成加入码或任务链接；
- 查看学生参与和提交状态。

#### D. 课堂汇总与复盘

教师可查看有权限的课程任务汇总：

- 班级常见论证缺口；
- 主要观点和分歧；
- 待核实的事实性陈述；
- 学生修改前后的论证变化；
- 可用于课堂继续讨论的问题。

学生个人练习默认不对教师开放。课程任务中应清楚说明哪些内容会被教师查看。

### 4.3 师生共同功能

- 课程议题和训练任务；
- 思维导图；
- 论证知识图谱；
- 训练报告导出；
- 历史记录、收藏和搜索；
- 服务状态、模型状态和错误提示；
- 反馈问卷与问题报告；
- 用户数据查看、删除和试用退出。

### 4.4 原有功能处理策略

| 原系统功能 | 新系统处理方式 |
|---|---|
| AI 正反方自动辩论 | 保留为不同立场示例和观点碰撞模式；增加论证结构与证据分析 |
| 人与 AI 辩论 | 保留并升级为核心论证训练方式之一 |
| AI 裁判总结 | 升级为按量表、有原文依据、提供具体改进建议的结构化报告 |
| 暂停、继续、轮次和加速 | 保留为 Web 训练会话的流程控制 |
| JSON 辩论存档 | 迁移为训练会话、观点版本和复盘记录；兼容旧存档导入 |
| 词云 | 可保留为辅助统计视图，不作为主要创新点 |
| ComfyUI 文生图 | 从首版主流程移除；可选云端图像 API 只用于封面配图 |
| AI 头像生成 | 改为预设头像或图片上传，避免等待生图服务 |

## 5. 创新性与竞争力

### 5.1 核心创新主张

**可追溯、可修订的师生协同论证训练闭环。**

创新方向不是简单增加大模型、多 Agent 或多个身份，而是：

1. 将 AI 从内容生成者转为分阶段的学习支架；
2. 反馈指向用户原文和具体论证缺口；
3. 记录观点形成与修订过程，支持训练复盘；
4. 同一套能力同时支持学生自主练习、教师个人训练和课堂教学；
5. 图谱体现关系依据和不确定性，允许用户编辑修正。

以上是设计主张，效果必须通过用户研究和测试验证。在验证前不可将其写成已证明的学习成效。

### 5.2 相较普通 AI 聊天产品

- 提供有步骤的议题训练，而非只有自由问答；
- 引导用户构建自己的论证，而非直接提供成稿；
- 展示论证关系、原文依据和不确定性；
- 允许用户修订和比较，而非只输出一次性评分；
- 支持师生课程任务闭环和教师个人训练；
- 可按任务、模型、时间和结果复现测试。

### 5.3 单 Agent 策略

首版采用**单个论证训练 Agent**，由后端程序按阶段安排模型调用：

1. 议题拆解；
2. 用户论证分析；
3. 生成一个或多个针对性追问；
4. 接收用户回答和观点修改；
5. 生成结构化复盘报告。

Agent 的流程由应用代码控制，不允许模型无限自主循环。不同阶段可以使用不同提示模板和输出 Schema，但底层先使用同一个 Agent 工作流。只有测试证明独立 Agent 协作带来明确收益时，才考虑引入多 Agent。

## 6. 技术架构

```text
Vue 3 Web 前端
├── 学生工作区
├── 教师工作区
├── 议题探索与训练
├── 报告、历史和版本比较
└── 思维导图/论证知识图谱
        │ REST API + SSE
        ▼
FastAPI 后端
├── 认证、角色、课程和权限
├── 训练任务与会话状态
├── 论证训练 Agent 工作流
├── 模型服务适配层
├── 结构化输出校验
├── 图谱与报告服务
└── 反馈与审计记录
        │
        ├── MySQL
        ├── 模型网关（本地/云端模型统一接入）【2026-10-13 修订：原 Ollama 表述由 v1.1 网关决策取代】
        └── 云端模型 API（可选）
```

### 6.1 前端技术

- Vue 3；
- TypeScript；
- Vite；
- Vue Router；
- Pinia；
- Element Plus 或 Naive UI；
- ECharts Graph 或 Cytoscape.js：知识关系图；
- Mermaid 或自定义树组件：思维导图；
- SSE：接收流式发言和训练进度。

选择 Vue 3 的原因：首版包含多角色、多页面、会话状态、图谱交互和复杂表单，组件复用与状态管理能降低后续维护成本。

### 6.2 后端技术

- Python；
- FastAPI；
- Pydantic：请求与模型输出校验；
- SQLAlchemy：数据访问层；
- Alembic：数据库迁移；
- SSE：模型生成内容与状态推送；
- 首版可用进程内任务管理；有更高并发需求后再引入 Redis/Celery 等任务队列。

### 6.3 数据库

**首版使用团队本机已部署的 MySQL。**

建议：

- 用户、课程、任务、会话、发言、报告使用关系表；
- 图谱节点和边先以校验后的 JSON 或关系表保存；
- 使用 `utf8mb4` 字符集和 InnoDB；
- 使用 SQLAlchemy 屏蔽业务逻辑与数据库细节；
- 使用 Alembic 管理表结构变更；
- 配置定期备份和数据清理策略；
- 明确学生个人训练与课程任务数据的访问权限。

### 6.4 模型服务适配

建立统一模型接口，例如：

- `generate_stream()`：生成训练对话和辩论文本；
- `generate_structured()`：生成议题结构、论证分析和复盘报告；
- `health_check()`：检测服务和模型是否可用。

首版经模型网关接入（MODEL_BASE_URL / MODEL_API_KEY / MODEL_DEFAULT 三键，OpenAI 兼容协议），复用现有代码；架构上留出兼容云端多模型渠道的能力。浏览器不直接访问模型服务，所有密钥只保存在后端环境配置中。【2026-10-13 修订：原"首版可继续用 Ollama"由 v1.1 网关决策取代】

结构化响应必须经过 Pydantic 校验。校验失败时有限重试，之后向用户提供清晰错误并保留已提交内容。

### 6.5 图表技术

- 思维导图：树状节点与父子关系；
- 知识图谱：节点、边、关系标签、证据来源；
- 前端使用 ECharts Graph 或 Cytoscape.js；
- 首版不引入 Neo4j，MySQL 可满足课程试点规模。

## 7. 思维导图与知识图谱实现

### 7.1 思维导图用途

用于展示一个议题的层级拆解：

```text
中心议题
├── 关键概念
├── 核心子问题
├── 分析视角
├── 待核实事实
└── 后续探索问题
```

### 7.2 论证图谱用途

节点类型：议题、主张、理由、证据、反例、来源、待核实项。  
关系类型：支持、反驳、补充、依赖、限制、需要证据。

### 7.3 生成与审核流程

1. AI 从用户论证和课程材料中抽取节点、关系和对应原文；
2. 后端校验 ID、节点类型、关系类型、文本长度和来源位置；
3. 无直接依据的关系标记为“AI 推断”或“待确认”；
4. 前端绘制可交互图谱；
5. 点击节点可查看对应发言或材料；
6. 用户和教师可编辑、删除或新增节点；
7. 图谱版本关联到观点修订记录。

### 7.4 示例数据格式

```json
{
  "nodes": [
    {"id": "topic", "type": "议题", "label": "课程议题"},
    {"id": "claim_1", "type": "主张", "label": "用户的核心观点", "source_ref": "message_12"},
    {"id": "reason_1", "type": "理由", "label": "用户给出的理由", "source_ref": "message_12"},
    {"id": "evidence_1", "type": "待核实", "label": "需要外部材料支持的事实主张"}
  ],
  "edges": [
    {"source": "topic", "target": "claim_1", "type": "讨论立场"},
    {"source": "claim_1", "target": "reason_1", "type": "理由支持"},
    {"source": "reason_1", "target": "evidence_1", "type": "需要证据"}
  ]
}
```

## 8. 页面与信息架构

1. **登录与角色入口**：学生或教师工作区；同一账号可按权限拥有多个角色。
2. **首页工作台**：继续上次练习、加入课程任务、创建个人探索。
3. **议题探索页**：概念、范围、子问题和多视角。
4. **训练页**：论点编辑区、人机追问、进度、阶段提示和控制操作。
5. **论证图谱页**：关系图、原文定位、编辑和待核实信息。
6. **复盘页**：量表反馈、观点版本比较、个人反思。
7. **教师任务页**：创建任务、目标、材料、加入码和提交要求。
8. **教师个人训练页**：议题分析、教学情境演练、复盘。
9. **班级汇总页**：课程共性问题、观点分歧和课堂讨论素材。
10. **历史与导出页**：训练历史、报告下载和数据删除。

视觉设计强调清晰的信息层级、状态反馈和图谱可读性。图表服务理解与复盘，不为页面数量而增加无关功能。

## 9. 主要 API 设计

| 方法与路径 | 功能 |
|---|---|
| `POST /api/auth/register` | 注册 |
| `POST /api/auth/login` | 登录 |
| `GET /api/me` | 获取当前用户、角色和权限 |
| `POST /api/courses` | 教师创建课程空间 |
| `POST /api/tasks` | 创建课程议题任务 |
| `GET /api/tasks` | 查询可访问任务 |
| `POST /api/tasks/{id}/join` | 学生加入任务 |
| `POST /api/sessions` | 创建个人或课程训练会话 |
| `POST /api/sessions/{id}/messages` | 提交观点或回应 |
| `GET /api/sessions/{id}/events` | SSE 流式输出和训练状态 |
| `POST /api/sessions/{id}/analyze` | 请求论证结构分析 |
| `POST /api/sessions/{id}/revisions` | 保存观点新版本 |
| `GET /api/reports/{id}` | 获取复盘报告 |
| `GET /api/teacher/tasks/{id}/summary` | 获取教师课程汇总 |
| `POST /api/feedback` | 提交用户体验反馈 |
| `GET /api/health` | 查看应用、数据库和模型状态 |

所有接口均须后端鉴权和资源级授权，不能只依赖前端隐藏入口。

## 10. 数据模型

建议首版至少包含：

- `users`：账号和基本资料；
- `user_roles`：学生、教师角色；
- `courses`：课程空间；
- `course_members`：课程成员及权限；
- `tasks`：议题、目标、材料、评价规则和提交要求；
- `sessions`：个人或课程训练会话；
- `messages`：用户和 AI 发言；
- `revisions`：观点不同版本；
- `argument_nodes`：图谱节点；
- `argument_edges`：图谱关系；
- `evidence_sources`：来源、引用位置和核验状态；
- `reports`：量表分析、依据和建议；
- `feedback_forms`：用户反馈；
- `audit_events`：模型版本、错误、耗时和重试记录。

个人训练默认私有。课程任务提交的可见范围需在任务页面明确说明。试点阶段仅收集实现功能和评估体验所必要的数据。

## 11. 安全、隐私与可靠性要求

1. 用户密码采用成熟的密码哈希方案保存，不存明文。
2. API 密钥、数据库密码通过环境变量或部署密钥配置管理，不提交进仓库。
3. 学生与教师数据按课程和任务边界授权访问。
4. 对上传材料设置文件类型、大小和内容校验。
5. 对模型输入设定长度上限和超时限制，避免单一任务占用过多资源。
6. 模型错误、超时和结构不合规要反馈到界面，不丢失用户已输入内容。
7. 支持用户删除个人练习和退出试用。
8. 图谱、评分和事实提示均保留原文或来源依据及不确定性标记。
9. 教师汇总优先展示去标识化的共性信息；个人内容按明确授权开放。
10. 按试点规模配置 MySQL 备份和恢复流程。

## 13. 测试与效果验证

### 13.1 软件功能测试

测试至少覆盖：

- 学生、教师及课程资源访问权限；
- 课程创建、加入、提交、报告查看；
- 人机训练完整流程；
- 暂停、继续、结束、重试；
- SSE 断线、重连和任务状态恢复；
- MySQL 事务、备份和恢复；
- 模型网关/API 不可用、超时、输出格式错误；【2026-10-13 修订：原 Ollama 表述由 v1.1 网关决策取代】
- 中文输入、长文本、空内容和无效数据；
- 常见桌面浏览器与平板布局。

### 13.2 AI 功能评测

建立覆盖不同课程议题的小型测试集并人工标注参考结果，评估：

- 主张、理由、证据、反例抽取准确性；
- 原文依据定位准确性；
- 论证关系识别有效性；
- 反馈与用户论证的相关程度；
- 结构化输出合规率；
- 延迟、超时和失败率；
- 同类输入重复运行的稳定性。

### 13.3 用户试点

邀请少量学生和教师完成真实课程议题练习：

- 学生在训练前后完成相似的短论证；
- 教师或独立评审按统一量表盲评；
- 记录学生是否根据反馈修订观点；
- 收集反馈清晰度、可操作性、完成耗时和再次使用意愿；
- 观察教师是否愿意用于课程任务和课堂复盘。

试点报告应说明人数、议题、评价流程、数据限制和未解决问题，不将小规模试用结果泛化为普遍效果。

## 15. 首版范围与暂缓项

### 首版必须实现

- 学生与教师账号和权限；
- 学生议题探索和人机论证训练；
- 教师个人思辨训练；
- 教师课程任务与学生提交；
- 结构化反馈和观点版本对比；
- 思维导图或论证知识图谱；
- MySQL 持久化；
- 模型可用性、失败恢复和用户反馈入口；
- 可现场演示的部署方案。

### 首版暂缓

- 多 Agent 协作；
- ComfyUI 生图；
- 完整教务、成绩和 LMS 功能；
- 特殊教育专用交互模式；
- 大规模高并发集群；
- 未经测试证明的学习成效承诺。

## 16. 主要风险和应对

| 风险 | 应对方式 |
|---|---|
| AI 反馈笼统或无依据 | 使用固定量表、引用原文、允许人工编辑并进行盲评测试 |
| 模型将错误内容表述得很确定 | 标记不确定性；来源缺失时标注待核实；不将生成当作事实核查 |
| 图谱关系生成错误 | Schema 校验、依据定位、用户可编辑、错误率纳入测试 |
| 需求范围过大 | 首版围绕单一课程训练闭环，延后非核心功能 |
| 本地模型速度和可用性不足 | 适配层支持本地/云端切换；限制长度、配置超时并提示状态 |
| 用户数据越权访问 | 后端资源级授权、默认私有、课程任务明确可见范围 |
| 教师或学生不愿持续使用 | 早期用户试点，采集操作阻碍和实际使用频率并据此缩减流程 |
| 文生图等待影响演示 | 首版不依赖生图；使用程序化图表和预设素材 |

## 17. 项目最终定义

> **思辨工坊是一款面向高校师生的 Web 议题研究与论证训练平台。学生使用议题拆解、人机对练、证据提示、论证图谱和观点修订进行练习；教师既可以开展个人议题思辨和教学情境演练，也可以设计课程训练任务、组织学生练习并开展课堂复盘。项目由现有 AI 辩论系统演进，以可追溯、可修订的师生协同论证训练闭环作为创新方向。**

项目具有参赛潜力，但最终竞争力取决于 Web 主流程是否稳定、AI 反馈是否有依据、教师与学生是否愿意实际使用，以及试点和测试能否给出可信证据。
